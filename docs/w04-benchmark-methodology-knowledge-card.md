# W4 知识卡片：Benchmark 方法论

> AI Infra Lab · Week 4 · 延迟/吞吐 · 百分位 · 预热 · 重复与方差

## 1. 延迟 vs 吞吐

- **延迟（latency）**：单个请求从发到收花了多久（ms）。
- **吞吐（throughput）**：单位时间完成多少请求或数据量（QPS、MB/s）。

两者相关但不是一回事。系统接近饱和时，吞吐不再上升，**延迟会急剧变差**（排队变长）。报告性能时应写成「在某吞吐下，延迟是多少」，只报其中一个数意义有限。

## 2. 百分位（P50 / P95 / P99）

平均值会把少数极慢请求抹平。把延迟从小到大排序：

| 符号 | 含义 |
|------|------|
| P50 | 中位数，典型体验 |
| P95 / P99 | 95% / 99% 的请求不慢于该值，反映长尾 |

一个页面常依赖多个后端；任一环节碰上长尾，整页就慢。SLO 常写成「P99 < 某阈值」，而不是只看平均值。

## 3. 预热（warm-up）

冷启动偏慢的常见原因：空 Page Cache、冷 CPU 缓存/分支预测、JIT 未编译、连接池未建好。

- **稳态测试**：先跑若干轮并**丢弃**，再正式计时。
- **冷启动测试**：每轮清缓存（如 `echo 3 > /proc/sys/vm/drop_caches`），并在报告中写明。
- **冷、热不要混在同一组统计里。**

## 4. 重复测量与方差

单次结果无法区分「真的变快」和「运气好」。同一配置跑 N 次，用：

- **均值**：平均水平
- **标准差**：散度
- **变异系数 CV = 标准差 / 均值**：一般 **CV < 5%** 视为较稳定

经验法则：两组均值差应**明显大于**各自波动，才谈得上「优化有效」。偶发尖刺（宿主机抢核、后台进程）会抬高均值和 CV，报告中应注明，必要时附剔除极端值后的统计。

## 5. 实验模板（本周实践）

固定结构：研究问题 → 假设 → 环境 → 基线 → **唯一变量** → 指标 → 结果 → 分析 → 局限。

### 研究问题

在同一台 VMware 虚拟机上，将 `hot.c` 从 `-O0` 改为 `-O2`，预热后各重复 10 次，task-clock 的下降是否在统计上可信？幅度多大？

### 假设

O2 的 task-clock 均值约低 30%；两组 CV < 5%；差距远大于波动。

### 环境与方法

- 主机：VMware 虚拟机；`perf` 7.0.14；`perf_event_paranoid=1`
- 无 PMU cycles，主指标 **task-clock**
- 负载：与 W3 相同的有限 `hot.c`（200×50×200000）
- 编译：`-O0` / `-O2`，均带 `-fno-omit-frame-pointer -g`
- 预热 3 次（丢弃）+ 正式 10 次；共两轮

### 结果

| 轮次 | 组别 | mean (ms) | std | CV | P95 (ms) |
|------|------|-----------|-----|------|----------|
| 1 | O0 | 2005.74 | 44.43 | 2.22% | 2051.44 |
| 1 | O2 | 1366.04 | 96.99 | 7.10% | 1364.45 |
| 2 | O0 | 1985.05 | 24.02 | 1.21% | 2008.87 |
| 2 | O2 | 1348.05 | 61.81 | 4.58% | 1350.62 |

- 相对 O0 的降幅：第 1 轮 ≈ 31.9%，第 2 轮 ≈ 32.1%（与 W3 单次约 -34% 接近）。
- 第 1 轮 O2 出现 1637ms 尖刺 → CV 超标；第 2 轮两边 CV 均 < 5%。
- 均值差约 640ms，远大于 O0 的 std（24–44ms），「O2 更快」结论可信。

### 分析与局限

1. 重复 + CV 才能证明加速比可信；单次碰巧接近真值不等于方法论完整。
2. 虚拟机共享宿主机，尖刺难以完全消除。
3. 本实验测的是 on-CPU 计算时间，不是跨请求的服务端 P99 延迟曲线；N=10 仍偏小。

## 6. 一句话带走

**先预热、再重复、报均值和 CV（以及需要时的百分位）；差距要压过噪声，冷热要分开说。**
