# W1 知识卡片：Linux CPU 性能诊断

## 1. 三个核心指标：各自衡量什么

| 指标 | 衡量的是 | 怎么看 | 容易误解的地方 |
|---|---|---|---|
| CPU 使用率 | 采样周期内，CPU 不空闲的时间占多少 | `top`、`mpstat -P ALL 1` | 多核机器要看单个核：总体 25% 可能是 4 核里有 1 核跑满（单线程瓶颈） |
| Load Average | 1、5、15 分钟内，处于可运行状态（R）加上不可中断睡眠状态（D）的任务数的指数平均值 | `uptime`、`top` 第一行 | 要和核数比较才有意义；Linux 把 D 状态也算进去，所以等 IO 也会把 load 推高 |
| 上下文切换 | 每秒有多少次从一个任务换到另一个任务 | `vmstat` 的 `cs` 列、`pidstat -w` | 本身没有好坏之分，要和自己的基线比较；突然暴涨才值得关注 |

经验判断：load 持续大于核数，说明有任务在排队；要分辨排队的是 R 状态还是 D 状态，看 `vmstat` 的 `r` 和 `b` 两列。

## 2. 上下文切换的本质

- **是什么**：内核把当前任务的寄存器、程序计数器、栈指针等执行现场保存起来，再恢复另一个任务的现场。保存的位置是内核里的 `task_struct` 和该任务的内核栈。
- **切换对象**：在 Linux 里，线程和进程都是 task，调度器切换的对象都是 task。同一进程内的线程共享地址空间，切换时不用换页表，开销较小；不同进程之间切换要换页表（`CR3` 寄存器），TLB 也可能失效，开销更大。
- **不算上下文切换的情况**：系统调用和中断只是从用户态进入内核态，属于模式切换，不会换任务，开销比上下文切换小得多。但中断处理结束后，如果唤醒了优先级更高的任务，就可能接着触发一次真正的切换。
- **代价**：直接开销是保存和恢复现场，单次大约几微秒；更大的是间接开销，包括 CPU 缓存和 TLB 被冲刷后，新任务刚开始运行时会频繁缓存未命中。

## 3. 两种切换：分别指向什么问题

| 类型 | 字段 | 发生原因 | 偏高时通常意味着 | 处理方向 |
|---|---|---|---|---|
| 自愿切换 | `cswch/s` | 任务主动让出 CPU：等锁、等 IO、`sleep`、等条件变量 | 锁竞争、频繁的小 IO、线程间频繁唤醒 | 减少锁粒度和锁持有时间，把 IO 改成批量或异步 |
| 非自愿切换 | `nvcswch/s` | 时间片用完，或被更高优先级的任务抢占 | 可运行的任务比 CPU 核数多，大家在抢 CPU | 减少线程数（一般和核数相当），绑定核心，降低 CPU 消耗 |

命令：`pidstat -w 1` 看进程级，`pidstat -wt -p <PID> 1` 细化到线程。

## 4. 怎么判断 CPU 饱和

两个条件**同时满足**才算饱和：
1. `vmstat` 的 `r` 持续大于 CPU 核数，说明有任务在排队等 CPU；
2. `id` 接近 0，说明 CPU 没有空闲。

辅助证据：非自愿切换明显增加；`pidstat -u` 里的 `%wait` 偏高；用 `perf sched` 或 `/proc/<pid>/schedstat` 能看到排队延迟。

区分"刚好跑满"和"饱和"：使用率 100% 但 `r` 小于等于核数，只是 CPU 被用得很充分；只有 `r` 远大于核数时，才真正出现排队、响应变慢。

## 5. Load 高但 CPU 使用率低

最常见的原因是大量任务处于 D 状态（不可中断睡眠），通常是在等磁盘 IO 或网络存储（比如 NFS 卡住）。

排查步骤：
1. `vmstat 1`：看 `b` 是否持续大于 0、`wa` 是否偏高；
2. `ps -eo pid,stat,wchan:32,cmd | awk '$2 ~ /D/'`：找出 D 状态的进程，`wchan` 列显示它卡在哪个内核函数上；
3. `iostat -x 1`：确认是哪块盘慢；
4. 也可能是锁或内核本身的问题，这时 `wa` 不一定高，需要结合 `wchan` 判断。

## 6. CPU 时间花在哪：各字段的含义

| 字段 | 含义 | 偏高时的常见原因 | 下一步 |
|---|---|---|---|
| `us` | 运行用户态代码 | 业务计算、序列化、压缩、正则表达式 | 用 `perf top` 或火焰图找热点函数 |
| `sy` | 运行内核态代码 | 系统调用太多、锁竞争（futex）、内存分配、网络收发 | 用 `strace -c` 统计系统调用，`perf top` 看内核函数 |
| `wa` | CPU 空闲，且有 IO 未完成 | 磁盘慢或 IO 太多 | 用 `iostat -x`、`iotop` 定位 |
| `hi`/`si` | 处理硬中断和软中断 | 网络包很多 | 看 `/proc/softirqs`，考虑网卡多队列、RPS |
| `st` | 被宿主机拿走的时间（虚拟机） | 宿主机资源超卖 | 换实例规格或宿主机 |
| `ni` | 运行降低了优先级的任务 | 后台批处理任务 | 一般无需处理 |

注意：`sy` 和 `cs` 都高，不一定是代码问题，也可能是线程数过多、日志同步刷盘或频繁小 IO 的配置问题。先用 `strace -c` 和 `perf` 拿到证据，再判断改代码还是改配置。`wa` 本质上是"空闲时间"的一种，`wa` 高不代表 CPU 很忙。

## 7. 标准排查流程：从整机到函数

1. **整机看大方向**：`vmstat 1`，判断问题偏 CPU（`r`、`us`、`sy`）、IO（`b`、`wa`）、内存（`si/so`）还是切换（`cs`）；用 `mpstat -P ALL 1` 看各核是否均衡。
2. **找到进程**：`pidstat -u 1` 看谁占 CPU，`pidstat -w 1` 看谁切换最多。
3. **细化到线程**：`pidstat -t -p <PID> 1`，或 `top -H -p <PID>`。
4. **细化到函数**：`perf top -p <PID>`，或 `perf record -g` 生成火焰图；Java 用 `jstack` 或 JFR。
5. **形成假设、修改、再复测**：每次只改变一个变量，按实验模板记录结果。

## 8. 常见的坑

- `pidstat` 和 `vmstat` 不加时间间隔时，输出的是开机以来的平均值；`vmstat 1` 的第一行同样是开机以来的平均值，读数时要跳过。
- 只看使用率，无法区分"刚好跑满"和"饱和"，一定要结合 `r` 一起看。
- 多核机器只看总体使用率，会漏掉单个核跑满的单线程瓶颈。
- 看到 load 高就认定是 CPU 问题，忽略了 D 状态任务的影响。
- Python 多线程受 GIL 限制，CPU 密集型任务开多个线程也只能用满一个核，要用多进程。
- 在虚拟机或容器里，要留意 `st` 和 cgroup 的 CPU 限制（`cpu.max`）；在 K8s 里被限流时，CPU 使用率可能不高但程序依然很慢。
